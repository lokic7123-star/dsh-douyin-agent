## 0. 结论速览

1. **计数口径线索不成立**：`unansweredCount=6` 与 `isOpenBacklogRecord` 过滤口径完全一致；已结案记录（autoHandled=true 且平台回执确认）不在 6 条内，也不会出现在 `/api/chat/unanswered` 的 items 里。若前端待答列表显示了已结案记录，数据源是 `state.contacts[].unanswered`（12 条**未过滤**原始数组）——纯展示口径分裂。
2. **DOM 窗口抖动线索部分成立**：15→14 条的窗口抖动真实存在（read_evidence 证据链记录），但对六条卡点**不是主因**。活跃队列 5 条记录的恢复核对（`mapBacklogMessages`，非 `compareMessageWatermark`）全部通过、补答队列 targets 已含这 5 条；**R1 的映射失败另列**（11-01 归档，`native-target-unavailable`）——其上下文快照与当前窗口零交集，目标消息早已挤出窗口，与抖动无关。「五条活跃记录映射通过」与「R1 映射失败」两件事并存，不构成矛盾。
3. **退避与上限线索成立且需修正认知**：`retryCount=20` 是**重试节奏计数**（指数退避，封顶 20 后固定 300s 间隔无限重试，无终态、无人工升级），不是失败次数上限；`generationAttempts=0` 仅说明**当前补答队列的生成计数为 0**——本次观察窗口内队列停在生成门槛之前，不外推到实时链路或历史轮次（C 节截图映射中的历史生成/发送各有独立证据）。
4. **复用条件线索部分推翻**：涉事记录卡在**更早的映射环节**（`mapBacklogMessages` 返回 `native-target-unavailable`——目标消息不在当前窗口），根本到不了已实现的"媒体目标复用旧文本"条件。"其目标之后有已发出回复导致复用失效"是理论上的第二重拦截，非当前实际卡点。
5. **分流线索推翻"两条链路不同资格判定"**：实时与补答共用同一条生成通道；插件装配层把聊天回复接进决策式模型通道（输出预算 512 token），输出超限即抛"未完整返回"错误。七次会话暂停全部是同类截断。被归档的五条不是被资格判定分流，而是被**随机输出长度**打断。
6. **直接死锁**：补答混合队列里 2 条媒体目标触发"targets 含媒体"门槛，3 条纯文本目标被**连坐**——拆分纯文本子集（经隔离回放验证后）可当场解开五条中三条的推进路径。

## B. 三个横切问题结论

### B1. 计数口径——后端正确，展示口径分裂

- 过滤函数：`isOpenBacklogRecord = record && !record.handledByUserAt && record.autoHandled!==true && !record.autoHandledAt`（chat-message.mjs:66）。已结案记录**保留在数组里**（审计设计，不删除），`autoHandledProof` 留作回执存证。
- 三个数据出口：
  - `/api/chat/unanswered`（`unanswered()`）：按同一口径过滤 → **6 条，不含已结案**；
  - `state().unansweredCount`（chat-service.mjs:300）：同一过滤 → **6**；
  - `state().contacts[].unanswered`（chat-service.mjs:299）：**未过滤的 12 条原始数组**，仅 UI 消费。
- 结论：已结案记录**不进入** 6 条计数与 unanswered 接口。若它"出现在待答列表"，唯一可能的前端数据源是 `contacts[].unanswered`。判定：**计数/过滤不是 bug，是展示口径分裂**。修法（纯展示）：前端改用 `/api/chat/unanswered`；或后端把 `contacts[].unanswered` 拆为 `open`/`done`（D 节数量三分）。

### B2. DOM 窗口不稳定对恢复核对的影响——真实信号，非主因

read_evidence 证据链（此前提交引入，本次首次派上用场）：

| 时刻(UTC) | messageCount | messageSetChanged |
|---|---|---|
| 15:24:16 | 15 | true（首读） |
| 15:25:17 | **14** | **true** |
| 15:30:20 | 14 | false |
| 15:35:20 / 15:40:20 / 15:45:20 | 14 | false |

- 恢复核对的真实执行者：`mapBacklogMessages`（chat-message.mjs:92-130）——把归档时 `recoveryEvidence.expectedContent` 的**完整后缀**在当前窗口指纹序列中做唯一匹配，native 目标要求 `messages.findIndex(id)` 在位且 `identitySource==='dom-message-id'`（:115-118）。`compareMessageWatermark`（chat-message.mjs:43-64，锚点必须在窗口末尾）只在**补答发送前**的发送前水位核对使用，不参与恢复映射。
- 对六条的影响：五条活跃记录（11-04）的 expectedContent（13–14 条）与当前 14 条窗口高度重叠，15→14 抖动**没有**阻断它们的映射（队列 targets 恰为这 5 条即证）。R1 的失败与抖动无关：其 15 条快照（止于 11-01 19:32）与当前窗口（最早 11-02 17:35）**零交集**，无论窗口稳定与否都无法匹配。
- 附带发现（证据链字段 bug）：read_evidence 的 `nativeIdCount` 恒为 0——`nativeId` 在 `publicMessages→identify` 阶段被剥离后统计，统计位置错误；应在剥离前的 raw 行上统计并透传。这解释了 dump 里 `nativeIdCount:0` 而映射仍走 native 路径的"矛盾"。

### B3. 退避与上限的真实语义

- `backlogPause`（chat-service.mjs:689-694）：`retryCount=min(20, n+1)`；`nextRetryAt=now+min(300s, 5000×2^min(n-1,6))`。retryCount 到 20 后**固定每 300s 重试一次，永不停止、无终态、无人工升级**——这就是"恒为 20、原因恒为同一码"的机制。
- `generationAttempts=0` 的含义：当前补答队列的生成计数为 0——`waiting-bounded-generation-evidence` 在生成门槛（chat-service.mjs:781）**之前** return，本次观察窗口内该队列没有发起过模型生成、生成预算没有因该队列消耗。该等待码的触发条件是合并 targets 中存在媒体/非文本/空文本目标——在混合队列里**永远为真**，与"等待证据到来"无关（证据不会自己长出来）。
- cap 语义总结：失败次数没有上限（无限每 5 分钟重试）；有上限的是"重试节奏加速"（20 档封顶）与"单上下文生成次数"（3 次/30 分钟，`generationContexts` 预算）。六条的实际落点：**永久等待态**，等价于设计上的"需人工"，但没有任何字段或事件把它升级为"需人工"——UI 只能靠 reason 文案间接感知。

## C. 实时/补答分流条件与截图消息映射

**分流机制还原**（不是两条链路不同资格，而是同一条链路的不同结局）：

1. 实时链路：`poll()` → `agent.reply()`（chat-agent.mjs:121-193）。聊天入口下 replyProvider 在装配处被设为决策式生成器（`maxTokens:512`，dsh-plugin.mjs:219、:286）——**聊天回复复用自主观看决策通道**。该通道在流式结束时要求 `finish.kind==='stop'`，否则抛"DSH 自主观看决策未完整返回（max-tokens），未执行动作。"（code=WATCH_DECISION_INCOMPLETE，native-watch-decision.mjs:51）。
2. 抛错 → `poll()` catch → `mark.status='paused'`（reason=上述错误文案）→ 下一 tick 归档 pending（"先前未完成的待答进入自动整理，继续接收可靠新消息。"）→ 进入 autoBacklog。
3. 补答链路：`processAutoBacklog` 用 ≤12 条纯文本上下文重新走**同一个** 512-token 通道生成。成功与失败取决于当次输出是否超限——11-04 17:13 补答成功（completionTokens=494，贴线未截断），其余多次失败（7 次会话暂停全为 max-tokens）。
4. 结构性问题：把**对话回复**路由进**决策式通道**（输出预算 512 token、错误文案还自称"自主观看决策"）。中文长回复极易越限；这不是随机的模型故障，是装配层的通道错配。

## D. 待答状态规则提案（对齐审核五态表）

五态：`正在补答` / `暂时失败可恢复` / `缺证据无法补答` / `发送结果不明` / `已回复或已结束`。

### D1. 记录级状态派生规则（可由现有字段计算，纯展示层可先行）

判定顺序（**发送结果不明优先于普通等待态**；「不在当前队列」本身不等于「缺证据无法补答」——缺证据态必须依据**明确的映射失败原因**，如 `native-target-unavailable` 这类具体码）：

1. **已回复或已结束**：`autoHandled===true` / `handledByUserAt` 存在 /（新增）人工结束标记存在。
2. **发送结果不明**：open 记录 `phase∈{sending,delivery-uncertain}` 或 `autoAttempt.state∈{reserved,uncertain}` 或 `legacyUncertain===true`，且尚未读回结案。
3. **正在补答**：open 记录在补答队列 archiveIds 中且 queue.state∈{model,sending,ready}，或 pending.phase='auto-backlog'。
4. **暂时失败可恢复**：在队列中且 queue.reason∈{bounded-generation-failed, waiting-zero-click-retry, waiting-native-outgoing-readback, waiting-contact-recheck}；或纯文本目标因队列混入媒体而受阻（连坐）。
5. **缺证据无法补答**：有**明确的映射失败码**（如 `native-target-unavailable`、`legacy-native-target-unavailable`、`qualification-evidence-unavailable`）持续成立；或媒体目标且无旧生成文本（生成门槛拒绝）。
6. 兜底：不满足以上任何一条的 open 记录归「暂时失败可恢复」并标注等待码——**不得**仅凭"不在当前队列"归入缺证据态。

当前六条对应：R1=缺证据（native-target-unavailable）；R2/R5/R6=暂时失败可恢复（连坐）；R3/R4=缺证据（媒体目标无旧文本，生成门槛拒绝）；发送结果不明当前为空（两条 uncertain 已读回结案）。

### D2. 后端需暴露的字段（记录级）

- `backlogState`：五态枚举（服务端派生，避免每个前端自行复刻判定规则）；
- `blockerCode`：明确的阻塞原因码（区分"映射失败-目标出窗""生成门槛-含媒体""生成失败-模型""读回等待"等），用于把结构性等待与暂时失败分开呈现；
- `progressNote`：人话进展（复用等待原因映射；"被媒体连坐"应明说"本条与暂不支持自动回复的媒体消息在同一批，需人工处理或拆分后重试"）；
- `availableActions`：`['mark-done','retry-now','open-chat']` 按态裁剪（缺证据态不给 retry-now，避免无效按钮）；
- `attempts` / 上次生成尝试时间：把**重试节奏计数**与**生成尝试次数**分开暴露（见 B3 的语义差异）。

### D3. "结束待答，不再回复"的服务端语义（需新增后端逻辑）

- **复用既有 `handledByUserAt` 人工结束字段**，不新造平行的结案标志体系；可加来源标记字段（如 `resolvedVia='panel'`）记录由哪个入口结束，保持单一结案事实源。
- 写入流程：控制锁内写入 → **persist → 重新 load 校验字段在位** → 才返回成功；失败保留原态并向 UI 报错。
- **运行中结束待答必须协调在途任务**：复用 `withChatPaused(resume:'preserve')` 语义（暂停→写入→不重建基线恢复），确保同一时刻没有并发发送/生成在写同一条记录。
- "结束待答后不会重发"的表述收敛为：**协调在途任务并经读回核对后才成立**——结束动作本身只持久化标记；不重发的保证由"结束后的记录不进入补答扫描 + 发送前的水位核对与防重复读回机制"共同构成，任何一环未经读回核对不得向用户宣称已完成。
- 结束后的记录：从补答队列 archiveIds 剔除、不计入 open 计数与到期判断；实现收口点是 `isOpenBacklogRecord`（chat-message.mjs:66）——它是待答口径的单一过滤点。**防重发以在途任务协调与恢复测试为准，人工结束标记只是条件之一**：标记写入后的链路行为（补答扫描、发送前水位核对、防重复读回）须经隔离恢复测试验证后才能宣称生效。

### D4. 数量三分（顶层与联系人级）

- `自动恢复中`（正在补答+暂时失败可恢复）、`需人工`（缺证据无法补答；发送结果不明超时未读回的并入此项并单独提示）、`已完成历史`（已回复或已结束）。
